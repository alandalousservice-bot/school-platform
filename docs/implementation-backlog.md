# وثيقة تنفيذ المنصة — خارطة العمل الموحدة

هذه الوثيقة هي المرجع التنفيذي الوحيد لاستكمال منصة تسيير المدرسة الابتدائية. تفصل بين ما هو موجود فعلًا، وما يحتاج إصلاحًا، وما يجب برمجته لاحقًا، حتى لا تختلط مهام المدير والأستاذ ومشرف المطعم أو مهام التصميم مع منطق البيانات.

## 1. حدود المشروع والقرارات الثابتة

- المنصة موجهة للمدرسة الابتدائية الجزائرية، بواجهة عربية RTL وهوية المؤسسة ووزارة التربية.
- الأدوار الأساسية: المدير، الأستاذ، مشرف المطعم. يمكن دعم مدير عام لاحقًا دون كسر صلاحيات المدير.
- الواجهة: React + Vite + PWA، والخادم: FastAPI، وقاعدة البيانات الحالية SQLite محلية.
- التشغيل المستهدف: Windows داخل المؤسسة، ومتصفح/تطبيق PWA على Android، مع قابلية النشر لاحقًا.
- المطعم يسجل وجبة الغداء فقط.
- لا تغيير في API أو RBAC أو مزامنة العمل دون اتصال أثناء مهام التصميم.
- لا تُضاف مكتبة خارجية أو خدمة سحابية إلا بقرار مستقل موثق.

## 4. خطة التنفيذ المرحلية

### المرحلة A — تثبيت الأساس

1. تشغيل `npm run lint` و`npm run build` من `frontend` وفحص `compileall` من `backend`.
2. معالجة تحذيرات lint الخاصة بتحميل البيانات في `AdminDashboard` و`BudgetManagement` دون تعطيل قاعدة lint.
3. فصل `AdminDashboard.jsx` إلى مكونات فرعية: `AdminSidebar`, `OverviewPanel`, `AttendancePanel`, `StudentsPanel`, `GradesPanel`, `SchedulePanel`, `InventoryPanel`, `StaffPanel`.
4. استخراج الثوابت العربية والأدوار والمواد إلى ملفات مسماة، مع منع تكرار التسميات.

### المرحلة B — تجربة البيانات الموحدة

1. تثبيت عقد `DataList`: الأعمدة، render، الفرز، البحث، pageSize، الحالة الفارغة، الكثافة.
2. تعميمه أولًا على سجل التدقيق والمستخدمين والمخزون.
3. إضافة فلاتر سياقية: الدور للمستخدمين، حالة المخزون، ونوع العملية لسجل التدقيق.
4. إظهار `Badge` للحالات فقط: متصل/غير متصل، منخفض/كافٍ، مسودة/مرسل/معتمد.
5. إضافة إخفاء/إظهار أعمدة مناسب للهاتف دون تغيير البيانات.

### المرحلة C — الإدخال والاستيراد

1. إنشاء `Field`, `SelectField`, `SearchField`, `FileDropzone`, و`SegmentedControl` مشتركة.
2. إضافة أيقونات بحث، رفع، مسح، سهم الاختيار من السبرايت المحلي.
3. استيراد Excel: معاينة، تعيين الأعمدة، كشف التكرار، كشف الباركود المكرر، تقرير أخطاء قابل للتنزيل.
4. جعل رفع الصور محليًا وآمنًا مع حد حجم وامتداد ورسالة عربية.

### المرحلة D — تجربة كل دور

**المدير:**

- ترتيب لوحة التحكم حول قرارات اليوم: الغياب، الاعتمادات، المخزون، الاتصال، والتنبيهات.
- إضافة مركز إشعارات يعرض نقاطًا تحتاج إجراءً، مع رابط مباشر إلى الوحدة.
- تحسين بطاقة التلميذ لتعرض الهوية، الولي، الصحة، الحضور، النقاط، والمرفقات بصلاحية المدير فقط.
- جعل اعتماد النقاط والتوزيع عملية واضحة ذات سجل تدقيق.

**الأستاذ:**

- تثبيت اختيار القسم/اليوم/الفترة كـsegmented control ملائم للّمس.
- إظهار حالة الاتصال والمزامنة وعدد العمليات المعلقة.
- منع تعديل دفتر النقاط بعد الإرسال إلا عبر دورة إعادة فتح صريحة من المدير.
- إضافة بطاقة تلميذ للعرض أثناء تسجيل الغياب والنقاط مع أقل عدد نقرات.

**مشرف المطعم:**

- جعل شاشة المسح هي الشاشة الأساسية وتعرض «وجبة الغداء» فقط.
- إضافة وضع إدخال يدوي عند تعذر القارئ.
- عرض رصيد المواد والتنبيه قبل نفادها، مع منع الرصيد السالب.
- إضافة تقرير يومي للوجبات المصروفة وحركة المخزون.

### المرحلة E — التقارير والاعتماد

1. توحيد ترويسة PDF: اسم المؤسسة، الولاية، الوزارة، الختم، التاريخ، المستخدم، ورقم الصفحة.
2. اعتماد لون واحد للطباعة وتباين مناسب للأبيض والأسود.
3. اختبار تصدير الغياب والنقاط والتوزيع والميزانية ببيانات عربية حقيقية.
4. إضافة اسم الملف وفترة التقرير بوضوح، ومنع تصدير بيانات غير معتمدة عند اشتراط الاعتماد.

### المرحلة F — الأمان والجودة والنشر

1. اختبارات RBAC لكل مسار؛ الأستاذ لا يصل إلى إدارة المدير والمطعم لا يعدل النقاط.
2. اختبارات منع التكرار والتعارض والرصيد السالب ووجبة غير الغداء.
3. نسخة احتياطية واسترجاع موثقان لقاعدة SQLite في التشغيل المحلي.
4. إعداد Windows: ملف تشغيل، تعليمات تثبيت، وتشغيل تلقائي اختياري.
5. إعداد Android PWA: manifest، أيقونة، offline fallback، اختبار تثبيت وتحديث Service Worker.
6. إعداد الإنتاج فقط بعد تحديد قاعدة بيانات وتخزين دائم وHTTPS ونسخ احتياطي.

## 5. تنظيم التسميات والبيانات

- «لوحة المدير» للوحدة الكاملة، و«لوحة الأستاذ»، و«لوحة مشرف المطعم».
- «إدارة الغيابات» لا «الحضور» عندما يكون المقصود تسجيل الغائبين.
- «دفتر النقاط» للواجهة، و`GradeEntry` داخليًا.
- «ملف التلميذ» للمعلومات الأساسية، و«بطاقة المتابعة» للملخص المتكامل.
- «التوزيع الأسبوعي» للجدول الناتج، و«الحجم الساعي» للقواعد المدخلة.
- «وجبة الغداء» ثابتة في المطعم، ولا تعرض الواجهة خيارات غير مدعومة.
- أي enum داخلي لا يظهر للمستخدم؛ يعرض نصًا عربيًا من `labels.js`.

## 6. قواعد منع خلط الأفكار

- كل مهمة يجب أن تنتمي إلى مرحلة ووحدة واحدة قبل تنفيذها.
- لا نخلط إعادة تصميم CSS مع تعديل API أو قاعدة البيانات في نفس commit إلا عند الضرورة.
- لا نضيف ذكاء اصطناعي أو خدمة خارجية أو تطبيقًا أصليًا قبل تثبيت النسخة المحلية الأساسية.
- لا ننشئ شاشة جديدة إذا كانت وظيفة الشاشة الحالية قابلة للتوسعة بمكوّن مشترك.
- لا نستخدم بيانات وهمية لإظهار رسوم أو مؤشرات؛ نستخدم حالة «لا توجد بيانات» عند غياب التاريخ.
- كل تغيير يجب أن يحافظ على الصلاحيات والعمل دون اتصال وسلامة بيانات النقاط والغياب.

## 7. معيار إغلاق كل مهمة

- الوصف والهدف واضحان.
- التغيير محصور في ملفات الوحدة المقصودة.
- `npm run lint` لا ينتج أخطاء.
- `npm run build` ينجح.
- `compileall` للخادم ينجح عند لمس Backend.
- اختبار يدوي للدور المتأثر يمر.
- لا أسرار أو بيانات إنتاج في Git.
- commit واحد برسالة واضحة، ثم رفع عادي دون force push.
- تحديث خانة المهمة في هذه الوثيقة.
